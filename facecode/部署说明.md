# 人脸修复服务 部署说明

阿里云函数计算 GPU + CodeFormer。按顺序做，每一步都有验收标准。

---

## 这个服务是干什么的

补上我们**完全没有**的那一环：人脸修复。

- 百度做的是**上色**，它只动颜色通道，不碰五官——这是它的优点，不是缺点
- 所以照片永远是「有颜色的糊脸」
- 这个服务把糊脸重建清楚，实测锐度 **2.4 → 113**（MyHeritage 水平约 115）

最终链路：

```
原图 → 人脸修复（这个服务）→ 上色（百度）→ 结果
```

先修脸再上色：上色器拿到干净的边缘，上出来的颜色更准。

---

## ⚠️ 先记住一件事

这个服务做的是**重建**，不是「修清楚」。

它把 150 像素的糊脸「想」成 512 像素的清晰脸。补出来的睫毛、牙齿、发丝，
**原照片里一个像素都没有**。想得很合理，但那是模型的想象。

所以：
- AI 标识必须保留，一个字都不能少
- 永远不能把结果说成「照片原本的样子」
- `w`（fidelity_weight）默认 **0.7**，宁可少编一点

## 第一步：建容器镜像仓库（ACR）

1. 阿里云控制台搜 **「容器镜像服务 ACR」** → 开通**个人版**（免费）
2. 地域选 **华东1（杭州）**——必须跟后面的 GPU 函数同地域，不然拉镜像要走公网，又慢又要流量费
3. 创建**命名空间**，比如 `zhizhiwu`
4. 创建**镜像仓库**，名字 `facecode`，代码源选 **「本地仓库」**

**验收**：仓库详情页能看到 `registry.cn-hangzhou.aliyuncs.com/zhizhiwu/facecode` 这样的地址。

---

## 第二步：构建镜像

⚠️ **不要在你的 Mac 上 `docker build`。** 你的 Mac 是 Apple Silicon（arm64），
FC 跑的是 amd64。跨架构构建这个 7 GB 的 CUDA 镜像，慢到不可接受而且容易失败。

**用阿里云云效或 ACR 的构建功能，在云上构建。** 两条路：

### 路 A（推荐）：ACR 从 Git 仓库自动构建

1. 把 `Dockerfile` 和 `app.py` 两个文件放进一个 Git 仓库（GitHub / Gitee / 云效 都行）
2. ACR 仓库详情 → **构建** → 绑定代码源 → 选那个仓库
3. 添加构建规则：分支 `main`，Dockerfile 路径 `/Dockerfile`，镜像版本 `latest`
4. 点**立即构建**

### 路 B：阿里云 Cloud Shell

1. 控制台右上角点 **Cloud Shell** 图标（终端样子）
2. 上传 `Dockerfile` 和 `app.py`
3. 执行：

```bash
docker login --username=<你的阿里云账号> registry.cn-hangzhou.aliyuncs.com
docker build -t registry.cn-hangzhou.aliyuncs.com/zhizhiwu/facecode:latest .
docker push registry.cn-hangzhou.aliyuncs.com/zhizhiwu/facecode:latest
```

**验收**：ACR 仓库的「镜像版本」里出现 `latest`，大小 **6~8 GB**。

⚠️ 第一次构建要 **20~40 分钟**（光 PyTorch 就 2 GB，权重 880 MB）。中间别关页面。

---

## 第三步：创建 GPU 函数

1. 函数计算 FC → **云函数** → **创建函数** → 选 **「GPU 函数」**
2. 配置：

| 项 | 填什么 | 为什么 |
|---|---|---|
| 函数名称 | `facecode` | |
| 运行环境 | 容器镜像 | |
| 镜像 | 选第二步推上去的那个 | |
| **GPU 显存** | **至少 8 GB** | CodeFormer + 人脸检测大约要 6~8 GB |
| 内存 | 8 GB 以上 | |
| vCPU | 跟着显存走，用默认 | |
| **执行超时** | **600 秒** | 冷启动要把权重读进显存，默认 60 秒不够 |
| 监听端口 | **9000** | 镜像里写死的 |

3. **环境变量**里加一条：

```
FC_SHARED_TOKEN = <自己生成一串，比如 openssl rand -hex 24>
```

⚠️ **这一条不能省。** HTTP 触发器挂在公网上，每次调用都烧 GPU 的钱。
不设的话，任何知道地址的人都能白嫖到你账单爆炸。

4. **实例数上限**先设 **2**。防止出 bug 时疯狂扩容烧钱。

---

## 第四步：开 HTTP 触发器

函数详情 → **触发器** → 创建 → **HTTP 触发器**

- 请求方法：勾 **GET** 和 **POST**
- 认证方式：**无认证**（我们在应用层用 `X-ZZ-Token` 自己把关了）

**验收**：拿到一个地址，形如 `https://facecode-xxxx.cn-hangzhou.fcapp.run`

---

## 第五步：验证服务本身

浏览器直接打开那个地址（GET /）。应该返回：

```json
{"ok": true, "device": "cuda", "cuda": true}
```

⚠️ **`device` 必须是 `cuda`。** 如果是 `cpu`，说明 GPU 没挂上——
函数能跑但一张要一分多钟，而且你还在按 GPU 的价付钱。这种情况去检查实例规格。

⚠️ 第一次打开可能要等 **40 秒以上**（冷启动）。第二次就快了。

---

## 第六步：接上腾讯云

1. 把 `zzFaceCode` 三个文件装进 `uniCloud-tcb/cloudfunctions/zzFaceCode/`
2. 编辑 `config.json`：

```json
{
  "endpoint": "https://facecode-xxxx.cn-hangzhou.fcapp.run",
  "token": "<跟 FC_SHARED_TOKEN 一模一样>"
}
```

3. 右键 `zzFaceCode` → 上传部署
4. 右键 → 本地运行，参数 `{"op":"ping"}`

**验收**：返回 `{ code: 0, msg: '通了', device: 'cuda', cuda: true }`

5. 再用真照片跑：`{"op":"enhance","fileID":"cloud://..."}`

**验收**：返回 `code: 0` 和一个新 `fileID`，`faces` 是检测到的人脸数。

## 常见的坑

| 现象 | 原因 |
|---|---|
| `device: "cpu"` | 函数没配 GPU 规格，或者选错了实例类型 |
| 第一次请求超时 | 冷启动。把调用方超时调到 300 秒以上 |
| 403 | 两边的 token 不一致 |
| `没找到人脸` | **这是正常结果不是故障**。侧脸、糊脸、合影里的小脸都可能检测不到。调用方要能跳过这一步继续走上色 |
| 构建失败卡在 pip | 换成阿里云的 pip 源 |
| 镜像推不上去 | ACR 和 FC 地域不一致 |

## 成本

- **按次**：没人用不花钱。粗估 1 分钱/张（热启动），冷启动那张 5~10 分钱
- **专属资源池**：预付费、没有冷启动，但不管用不用都在扣。现在日活个位数，**不要买**

⚠️ 上面是估算。准确数字用 FC 控制台左边的**「价格计算器」**算，
或者跑几十张之后看**「成本中心」**的真实账单。
